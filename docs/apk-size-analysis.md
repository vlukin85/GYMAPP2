## Разбор внутри групп

### lib/ — 40,9 МБ, две полные копии нативного кода

Каждая из 25 библиотек лежит в двух архитектурах. Дубль `armeabi-v7a` стоит **16,6 МБ (23 % APK)**. Самые тяжёлые на arm64: `libreactnative.so` 5,7 МБ, `libbarhopper_v3.so` 4,8 МБ (сканер штрихкодов ML Kit), `libhermes.so` 2,1 МБ, `libreanimated.so` 1,4 МБ, `libappmodules.so` 1,4 МБ, `libexpo-modules-core.so` 1,3 МБ, `libc++_shared.so` 1,3 МБ, `libavif_android.so` 0,9 МБ.

### assets/ — 4,8 МБ

### Чего в APK нет

**Фотографии упражнений и миниатюры продуктов (334 позиции) в APK не входят** — `assets/exercise-photos` отсутствует, весь медиаконтент каталожного типа скачивается на устройство по требованию (загрузка по Wi-Fi в настройках). Дальнейший рост каталога фото APK не раздувает.

## Выводы и рекомендации

1. **Главный резерв — переход на arm64-only (todo 825).** Устройства на чистом 32-битном ARM сегодня — редкость; отказ от `armeabi-v7a` в release-сборке экономит ~16,6 МБ (APK станет ≈ 56 МБ). В workflow `.github/workflows/android-apk.yml` выбор `debug_architecture: arm64-v8a` для debug-сборки уже есть — остаётся повторить тот же механизм для release (ABI-сплиты или `abiFilters "arm64-v8a"` в `expo-build-properties`), сохранив универсальную сборку как опцию ручного запуска.
2. **Картинки ресурсов: JPEG → WebP.** 5,92 МБ JPG и 3,04 МБ PNG в `res/` — это встроенные изображения интерфейса. Перекодировка в WebP (качество ~80) обычно даёт −25…−40 %, для прозрачных PNG — `-lossless` или WebP с альфой: суммарная экономия ориентировочно 2–3 МБ. Часть PNG уже в WebP (0,62 МБ) — миграцию можно продолжить тем же инструментом (`cwebp`).
3. **Звуки сигналов: WAV → OGG/Opus.** Четыре `.wav` (0,75 МБ) — несжатый PCM; перекодировка в OGG Vorbis/Opus сократит их до ~0,1 МБ без слышимой потери. Плюс проверка плотности: одна и та же картинка не должна лежать в нескольких `drawable-*dpi`.
4. **Сканер штрихкодов — тяжёлый и опциональный.** `libbarhopper_v3.so` + модели = ~9 МБ на arm64 (и ещё ~6,5 МБ дублем под 32-бит). Вариант: отдельная сборка без сканера или динамическая поставка ML Kit (Play Feature Delivery) — уместно, если сканирование продукта используется редко.
5. **`resources.arsc` 1,85 МБ** — симптом большого числа дублированных плотностей; выравнивание ресурсов по одной плотности (xxhdpi) дополнительно сэкономит и в `res/`.
6. **Реалистичный итог после шагов 1–3: ~52–56 МБ** вместо 72,6 МБ (−25 %), без потери функциональности для подавляющего большинства устройств.
